# 3X-UI 流量计数器回退统计设计

## 意图

限时套餐续费会重置 3X-UI 3.4.2+ 的服务器级客户端流量。当前流量同步发现远端累计值小于 `traffic_sync_log.last_sync_traffic` 时，只更新基线而不累计远端重置后已经产生的流量，造成该部分流量丢失。

## 目标

- 将 3X-UI 流量视为可重置的单调计数器。
- 正常增长时继续按“当前值减上次基线”计算增量。
- 计数器回退时，将当前值视为重置后产生的增量，并立即计入 `users.traffic_used`。
- 两种分支都将 `traffic_sync_log` 更新为当前远端累计值。
- 管理端最近一轮服务器流量统计使用完全相同的回退算法，保证展示值与实际入账值一致。
- 保留流量统计倍率：所有原始增量统一乘以 `traffic_usage_multiplier` 后四舍五入。

## 非目标

- 不修改续费支付事务。
- 不主动删除或清零 `traffic_sync_log`。
- 不修改 3X-UI 同步任务及其重试条件。
- 不新增数据库字段或迁移。
- 不处理 3X-UI 3.4.2 以下按 inbound 独立重置的兼容问题；生产环境已经全部升级到 3.4.2。
- 不在本次修复中扩展处理流量任务与续费事务并发写 `users.traffic_used` 的独立竞态。

## 方案比较

### 方案一：续费事务直接清理同步基线

优点是清理动作天然只执行一次。缺点是远端重置失败或延迟时，下一轮统计会把远端旧累计值当作新流量重新计入，因此不采用。

### 方案二：增加一次性“待重建基线”状态

可以隔离远端重试，但需要新增状态、迁移和消费逻辑，复杂度明显高于本问题所需，因此不采用。

### 方案三：按可重置计数器计算增量（选定）

正常情况下使用差值；发生回退时使用当前值作为增量。该方案不耦合续费和 3X-UI 重试，能在重置成功后补记已经产生的流量，且无需数据库迁移。

## 计算规则

对每个 `user_id + server_id`：

```text
若 currentTraffic >= lastSyncTraffic：
    rawIncrement = currentTraffic - lastSyncTraffic
否则：
    rawIncrement = currentTraffic

increment = round(rawIncrement * trafficUsageMultiplier)
newBaseline = currentTraffic
```

回退日志应明确说明检测到远端计数器重置、当前值被作为本轮原始增量，以及同步基线将更新为当前值。当前值为 0 时，本轮增量仍为 0。

## 数据一致性

`traffic-manager` 负责实际用户流量入账，`traffic-usage-stats-service` 负责管理端最近一轮服务器统计。两处必须共享相同语义：回退时都使用 `currentTraffic`，避免管理端图表显示 0 而用户流量实际增加。

## 验证范围

- 正常增长：`last=100`、`current=200`，原始增量为 `100`。
- 计数器回退且当前非零：`last=200`、`current=100`，原始增量为 `100`。
- 计数器回退到零：`last=200`、`current=0`，增量为 `0`。
- 同步失败但远端计数未变化：`last=current`，增量为 `0`。
- 倍率：回退后的当前值也必须乘以配置倍率并四舍五入。
- 管理端快照：回退分支的服务器总量和用户明细与实际入账增量一致。

## 约束与风险

- 本设计依赖生产环境 3X-UI 全部为 3.4.2+，服务器级客户端流量重置是整体操作。
- 算法假设成功获取的累计值下降代表计数器重置；若面板返回成功但数据是瞬时错误值，仍可能造成基线异常，这属于外部数据可信度问题，不在本次范围内。
- 修改 `server/**/*.js` 后需要提醒重启服务器，但不得由开发流程自行启动服务器。
