# CF IP 50 选 5 优选逻辑设计

## 目标

将用户端 CF IP 优选流程由“随机 20 选 5”调整为“随机 50 选 5”，提升测试样本量，并以丢包率作为首要质量指标。候选列表在 IPv6 池数量充足时固定包含 3 个 IPv6；最终推荐结果在存在可连通 IPv6 时保留 1 个 IPv6 作为兜底。

## 候选 IP 抽取

后端 `getCfIps()` 每次从启用的 CF IP 池中随机返回最多 50 个候选：

- IPv6 池不少于 3 个时，随机抽取 3 个 IPv6。
- IPv6 池不足 3 个时，返回全部可用 IPv6。
- 剩余名额由随机 IPv4 补足。
- 合并后再次随机打乱，避免地址类型集中展示。
- 当启用 IP 总数不足 50 个时，返回所有可用候选，不重复补位。

## 浏览器测速

每个候选 IP 在浏览器中执行 5 次连通性测试，单次超时时间为 3 秒。测试间隔继续使用现有配置，避免对同一地址连续发起过密请求。

测速通过动态并发池调度：

- 同时处于测试状态的 IP 最多为 10 个。
- 任一 IP 完成全部 5 次测试后，立即从等待队列补入下一个。
- 不采用固定批次等待，避免一个慢 IP 阻塞同批其他 IP 完成后的空闲并发槽。
- 单个 IP 测试异常只记录为该次失败，不中断其他 IP。

每个 IP 记录测试次数、成功次数、平均延迟和丢包率。丢包率按 `1 - 成功次数 / 测试次数` 计算；平均延迟只统计成功请求。

## 排序与推荐

测试结果按以下优先级排序：

1. 已完成且至少连通一次的 IP；
2. 丢包率从低到高；
3. 平均延迟从低到高；
4. 不可用或未完成测试的 IP 排在末尾。

“选前 5”按以下规则生成推荐结果：

- 若存在可连通 IPv6，先保留排序最靠前的 1 个 IPv6 作为兜底。
- 其余名额按排序结果优先选择 IPv4。
- IPv4 不足 4 个时，再使用剩余可连通 IPv6 补足。
- 若没有可连通 IPv6，则直接选择排名最靠前的最多 5 个可连通 IPv4。
- 可连通 IP 总数不足 5 个时，选择全部可连通 IP，并沿用现有提示方式反馈实际数量。

手动选择仍限制最多 5 个 IP，应用接口及数据库结构不变。

## 代码边界

后端仅负责候选池抽取，不参与测速，以确保测试结果反映用户当前网络而非服务器网络。

前端将并发调度、结果比较和推荐选择拆分为职责清晰且带注释的工具函数，页面组件负责状态展示、消息提示和调用工具函数。现有测速参数配置继续作为次数、超时、间隔和最大并发数的统一来源。

## 验证

采用测试驱动方式覆盖以下行为：

- 候选池在数据充足时返回 50 个 IP，且包含 3 个 IPv6。
- IPv4、IPv6 或总池数量不足时正确降级且不重复。
- 最大并发测试数不超过 10，并在任务完成后及时补位。
- 每个 IP 测试 5 次，单次超时配置为 3 秒。
- 丢包率优先于平均延迟排序。
- 存在可连通 IPv6 时推荐结果包含且仅保留 1 个最优 IPv6；IPv4 不足时允许额外 IPv6 补位。
- 没有可用 IPv6、可用 IP 不足 5 个及全部不可用等边界场景。
