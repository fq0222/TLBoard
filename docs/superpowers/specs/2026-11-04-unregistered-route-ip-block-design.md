# 未注册路由 IP 临时封禁设计

## 意图

针对自动化路由扫描：同一来源 IP 在 10 分钟内累计访问 2 次未注册路由后，临时封禁该 IP 30 分钟，降低无效请求和扫描日志噪声。

## 目标与边界

- 用户端与管理端 Express 应用都纳入保护，并共享同一份进程内状态。
- 仅请求最终落入应用的兜底 404 处理器时，才算一次“未注册路由访问”。
- 第二次未注册路由请求仍返回原有 404，同时开始 30 分钟封禁；封禁期间后续 HTTP 请求返回 429，并携带 `Retry-After`。
- 已注册路由产生的参数错误、鉴权失败或业务 404 不计数。订阅链接、下载链接、密码重置 token 以及其他动态参数路由因此不受影响。
- 不改变现有登录、注册、邮件、Passkey 和订阅无效 token 限流器的行为。

## 非目标与反目标

- 不做永久黑名单、管理后台解封界面或数据库审计记录。
- 不根据响应状态码笼统计数，避免将已注册路由的业务 404 误判为扫描。
- 不在扫描流量下持续写 PostgreSQL，避免防护本身放大数据库压力。
- 不依赖 URL 中 token 的格式或内容维护例外名单。

## 实现约束

- 新增带内部状态的封禁模块时使用 `class` 封装，并补充职责、参数及核心分支注释。
- 使用项目现有 IP 归一化工具：IPv4 按单地址统计，原生 IPv6 按 `/64` 统计。
- 信任 Express 已解析的 `req.ip`；现有 `trust proxy` 配置保持不变。
- 状态保存在单进程内存中；应用重启后自动清空，适配当前单实例部署。
- 过期的计数和封禁记录惰性删除，并进行定期清理，避免 Map 随扫描 IP 数量无限增长；清理定时器不得阻止 Node.js 进程退出。
- 429 响应沿用 JSON 包装格式，不泄露内部计数；日志只记录归一化 IP、封禁时长及必要请求信息。

## 状态语义

1. 首次兜底 404：记录计数 1，返回原有 404。
2. 10 分钟内第二次兜底 404：建立 30 分钟封禁，返回原有 404。
3. 封禁期间任意 HTTP 请求：在业务路由前直接返回 429，并设置向上取整秒数的 `Retry-After`。
4. 超过 10 分钟未达到阈值：旧计数失效，下次从 1 开始。
5. 封禁到期：删除封禁和旧计数，请求恢复正常。

## 方案比较

- **应用层共享内存（已选）**：能以是否进入兜底路由为准确判据，不增加数据库压力；代价是重启清空且不跨进程共享。
- **PostgreSQL 状态**：支持重启和多实例共享，但扫描流量会带来额外数据库读写。
- **Nginx/Fail2ban**：更靠近网络入口，但无法可靠区分未注册路由和已注册路由中的无效 token，误封风险较高。

## 验证

- 单元测试覆盖首次 404、第二次触发、封禁响应、30 分钟到期、10 分钟计数过期、IPv4/IPv6 键归一化和清理行为。
- 应用装配测试覆盖用户端与管理端共享封禁状态。
- 回归测试证明已注册的订阅、下载和密码重置 token 路由不会增加未注册路由计数。
- 按项目要求运行相关 `server/test/` 测试脚本，并在交付时展示完整测试日志。
