# 个人提现与余额流水功能设计

## 1. 背景与目标

项目已经具备用户余额、推广奖励入账和余额支付套餐的基础能力，但余额变动尚未形成统一、可审计的流水，用户也无法提交个人提现申请。

本功能需要完成以下目标：

- 在用户端“我的”页面提供收款信息管理、余额与累计推广奖励展示以及提现入口。
- 用户上传微信或支付宝收款二维码后，由服务端解析二维码内容；原始图片不持久化。
- 新增独立提现页面，提供提现申请和余额明细查询。
- 为推广奖励、余额支付套餐、提现扣款及提现驳回退款建立统一余额流水。
- 在管理端新增独立的用户余额管理页面，供管理员查询余额、奖励、流水并处理提现。
- 在系统设置中提供最低提现金额配置，默认 20 元。
- 通过统一余额服务和 PostgreSQL 事务保证实时余额、业务记录与余额流水一致。

## 2. 已确认的业务规则

### 2.1 提现规则

- 金额统一以“分”为数据库存储单位，用户输入最多两位小数。
- 最低提现金额由管理端系统设置维护，默认值为 2000 分（20 元）。
- 不收取提现手续费，申请金额、余额扣减金额和管理员实际转账金额相同。
- 用户提交提现申请时立即扣减余额，不等待管理员处理。
- 同一用户同一时间最多存在一笔 `pending` 状态的提现申请。
- 用户不能自行撤销提现申请。
- 管理员确认转账后，提现状态变为 `completed`，不再次扣减余额。
- 管理员可以驳回申请，但必须填写驳回原因。驳回时自动退回余额并记录退款流水。
- 已完成或已驳回的提现申请不可重复处理。
- 管理员确认完成后不可通过产品界面撤销；异常纠错由数据库运维处理。
- 所有已登录管理员均可查看和处理提现。

### 2.2 收款码规则

- 每位用户只保存一个当前收款码，可在微信和支付宝之间更换。
- 用户先选择收款码类型，再上传图片。
- 支持 PNG、JPEG 和 WebP，文件大小上限为 5 MB。
- 服务端负责读取图片、解析二维码并校验内容与用户选择的平台是否一致。
- 微信收款码识别常见微信支付协议，例如 `wxp://`、`weixin://wxpay/`。
- 支付宝收款码识别官方收款链接，例如 `https://qr.alipay.com/`。
- 无法解析、同时包含多个二维码、平台不匹配或二维码内容超限时拒绝保存。
- 原始上传图片只用于本次解析，不写入数据库或长期文件存储。
- 数据库保存收款方式、加密后的二维码内容、内容摘要和更新时间。
- 每笔提现申请保存申请时的收款方式与二维码密文快照，用户之后更换收款码不会影响历史申请。
- 管理端展示的是根据已解密内容重新生成的等价二维码，不是用户上传的原始图片。

### 2.3 余额流水规则

- 流水上线后，任何余额变化都必须在更新 `users.balance` 的同一个事务中写入流水。
- 流水记录不可由产品功能修改或删除。
- 首次迁移时，为每位现有非零余额用户写入一笔“期初余额”流水；不尝试伪造历史业务明细。
- 需要记录的流水类型包括：
  - `opening_balance`：期初余额。
  - `referral_reward`：推广奖励入账。
  - `plan_payment`：使用余额支付套餐。
  - `withdrawal`：提交提现申请时的余额扣减。
  - `withdrawal_refund`：提现被驳回后的余额退回。
- 流水金额使用有符号整数：入账为正数，扣款为负数。
- 每笔流水保存变动后的余额，用于展示和审计。
- 管理端不提供人工增加或扣减余额的能力。

## 3. 技术方案

采用“集中式余额服务 + 不可变流水”方案：继续使用 `users.balance` 作为高效查询的实时余额，同时新增不可变流水作为审计依据。所有余额变动统一经过余额服务完成。

相较于完全通过流水聚合余额，此方案能保留现有用户查询和余额排序性能；相较于在各业务模块中分散追加日志，统一服务能降低漏记和余额与流水不一致的风险。

## 4. 数据模型

### 4.1 `balance_transactions`

余额流水表，建议字段如下：

- `id`：主键。
- `user_id`：用户 ID，关联 `users.id`。
- `type`：流水类型。
- `amount`：有符号变动金额，单位分，不能为 0。
- `balance_after`：变动后的用户余额，单位分，不能小于 0。
- `reference_type`：关联业务类型，例如 `referral_reward`、`order`、`withdrawal_request`。
- `reference_id`：关联业务记录 ID。
- `description`：面向用户和管理员的简短说明。
- `created_at`：创建时间。

约束与索引：

- 按 `user_id, created_at DESC, id DESC` 建立查询索引。
- 对可唯一确定的业务关联建立唯一约束，防止相同推广奖励、订单支付或提现业务重复记账。
- 流水只允许插入和查询，业务代码不提供更新与删除方法。

### 4.2 `user_payment_qr_codes`

用户当前收款信息表，建议字段如下：

- `id`：主键。
- `user_id`：用户 ID，唯一并关联 `users.id`。
- `payment_type`：`wechat` 或 `alipay`。
- `qr_payload_encrypted`：二维码内容密文。
- `qr_payload_digest`：二维码内容摘要，用于审计与去重，不用于还原内容。
- `created_at`、`updated_at`：创建和更新时间。

删除用户时级联删除当前收款信息。

### 4.3 `withdrawal_requests`

提现申请表，建议字段如下：

- `id`：主键。
- `user_id`：用户 ID。
- `amount`：申请金额，单位分。
- `status`：`pending`、`completed` 或 `rejected`。
- `payment_type`：申请时的收款方式快照。
- `qr_payload_encrypted`：申请时的二维码内容密文快照。
- `qr_payload_digest`：申请时的内容摘要快照。
- `reject_reason`：驳回原因，仅驳回时填写。
- `processed_by`：处理管理员 ID。
- `processed_at`：处理时间。
- `created_at`：申请时间。

约束与索引：

- 对 `user_id` 建立仅覆盖 `status = 'pending'` 的唯一索引，从数据库层保证每个用户最多一笔处理中申请。
- 按 `status, created_at DESC` 和 `user_id, created_at DESC` 建立管理端查询索引。
- 状态字段、金额和驳回原因使用数据库约束保护基本合法性。

### 4.4 系统设置

在 `system_settings` 中新增 `minimum_withdrawal_amount`，值以分为单位保存，缺失时后端使用 2000 分作为默认值。管理端界面以元为单位输入和显示。

## 5. 统一余额服务

新增职责单一的余额服务，封装余额变更和流水写入。服务不自行开启嵌套事务，而是接收事务连接，供推广奖励、订单支付和提现业务复用。

核心操作包括：

- 增加余额并写入流水。
- 在余额充足的条件下扣减余额并写入流水。
- 查询用户余额明细与筛选结果。
- 使用业务引用唯一键保证相同业务不会重复记账。

所有余额写操作使用数据库事务和用户行锁。操作顺序为：锁定用户记录、校验当前余额和业务状态、更新余额、写入流水、写入或更新关联业务记录、提交事务。任一步失败都回滚。

### 5.1 推广奖励接入

现有首单推广奖励逻辑保留其幂等约束，但余额累加改为调用统一余额服务。推广奖励记录、用户余额和 `referral_reward` 流水必须在同一个专用数据库连接和事务中完成。

### 5.2 余额支付接入

现有套餐余额支付流程改为调用统一余额服务。订单创建、余额扣减和 `plan_payment` 流水必须在同一事务中完成。若订单或余额处理失败，全部回滚。

### 5.3 提现申请与处理

提交申请时：

1. 读取并验证最低提现金额配置。
2. 开启事务并锁定用户记录。
3. 校验当前收款码、余额和处理中申请。
4. 创建包含收款信息快照的提现申请。
5. 扣减余额并写入 `withdrawal` 流水。
6. 提交事务。

管理员确认时，仅以条件更新将 `pending` 改为 `completed`，保存处理管理员与时间，不产生新流水。

管理员驳回时，在事务内锁定提现申请和用户记录，将状态改为 `rejected`、保存原因与处理人、退回余额并写入 `withdrawal_refund` 流水。

## 6. 二维码解析与加密

### 6.1 解析流程

- 上传使用内存缓冲区，不把原图写入永久目录。
- 校验 MIME 类型、实际图片格式、文件大小和图片尺寸，防止伪造文件及过度资源消耗。
- 解码图片中的二维码，要求仅得到一个非空结果。
- 对解码内容设置合理长度上限。
- 根据用户选择的平台执行协议和域名白名单校验。
- 校验通过后立即加密二维码内容并丢弃图片缓冲区。

平台协议白名单需要集中定义并配套测试，后续遇到官方格式变化时可局部扩展。未知格式默认拒绝，不能仅凭用户选择的平台类型放行。

### 6.2 加密方案

- 使用带认证的对称加密方式，例如 AES-256-GCM。
- 每次加密使用独立随机 IV，并保存版本、IV、认证标签和密文。
- 密钥由新环境变量提供，不写入 `config.js` 默认值、PM2 配置真实值、日志或 Git 仓库。
- 应用启动或首次调用相关功能时校验密钥格式；密钥缺失时明确禁止保存、展示和提交提现，不能回退到明文。
- 二维码明文和完整密文均不得写入应用日志。
- 管理端二维码展示接口必须经过管理员鉴权，并设置禁止浏览器长期缓存的响应头。

## 7. 用户端设计

### 7.1 “我的”页面首卡

替换 `client-user/src/views/user/My.vue` 的第一张“账户信息”卡，不修改用户首页 `Profile.vue`。

新卡片参考用户提供的收款信息样式，包含：

- 标题和用途说明。
- 当前余额。
- 累计推广奖励总额。
- 微信/支付宝收款方式选择。
- 二维码上传区域、解析状态和已保存状态。
- 保存/更换收款码按钮。
- 跳转独立提现页的“提现”按钮。

未设置有效收款码时，提现按钮不可用并提示先保存收款码。原卡片中的邮箱、套餐、到期时间、流量使用、订阅状态和“前往服务台”入口不在该位置继续展示。

### 7.2 独立提现页面

新增用户路由和独立页面。桌面端参考示意图采用左右布局：

- 左侧：当前余额、累计推广奖励、最低提现金额、提现金额输入、提交按钮和当前处理中状态。
- 右侧：余额明细列表。

明细支持：

- 关键词搜索，匹配流水说明。
- 按流水类型筛选。
- 服务端分页。
- 展示时间、类型、说明、增减金额和变动后余额。

用户端不提供单独的提现申请历史列表。提现申请、完成状态和驳回退款通过余额明细体现；若当前存在 `pending` 申请，则左侧直接展示处理中金额并禁用再次提交。

移动端改为上下排列，表格转换为可读的卡片式明细，避免横向滚动成为主要交互。

## 8. 管理端设计

### 8.1 用户余额管理页面

新增独立菜单、路由和页面，包含用户余额列表：

- 邮箱。
- 当前余额。
- 累计推广奖励。
- 当前处理中提现金额和状态。
- 邮箱搜索与服务端分页。

点击用户后打开详情抽屉或弹窗，展示：

- 用户余额和累计奖励概览。
- 该用户完整余额流水，支持类型筛选和分页。
- 当前处理中提现申请的金额、申请时间、收款方式和重新生成的二维码。
- “确认完成”和“驳回”操作。

确认和驳回均要求二次确认。驳回必须输入非空原因。页面不提供人工调账。

### 8.2 系统设置

在现有系统设置页新增最低提现金额字段：

- 输入和展示单位为元。
- 默认值为 20 元。
- 只允许大于 0 且最多两位小数的金额。
- 保存时转换为分，后端独立校验，不能只依赖前端。
- 配置修改只影响之后提交的提现申请，不改变已提交申请。

## 9. API 设计边界

用户端新增接口职责：

- 查询余额与收款信息摘要。
- 上传、解析并保存当前收款码。
- 查询提现页概览和当前处理中申请。
- 提交提现申请。
- 分页查询个人余额流水。

管理端新增接口职责：

- 分页查询用户余额汇总。
- 查询指定用户的余额概览和流水。
- 查询处理中提现详情；二维码由服务端解密后直接生成图片响应，不向浏览器返回二维码明文。
- 确认提现完成。
- 驳回提现并退款。

系统设置接口扩展最低提现金额字段。所有接口沿用项目现有鉴权、中间件、参数验证和 `{ code, message, data }` 响应结构。

为减少敏感信息暴露，所有 JSON 接口均不返回二维码明文。受保护的管理端二维码接口只返回服务端生成的图片，并设置禁止缓存的响应头。

## 10. 错误处理与并发保护

以下情况必须返回明确业务错误，且不能产生部分写入：

- 未设置或无法解密收款码。
- 二维码无法解析、类型不匹配或格式不受支持。
- 提现金额格式错误、低于最低金额或高于当前余额。
- 用户已有处理中申请。
- 管理员处理的申请不存在、已完成或已驳回。
- 驳回原因为空。
- 加密密钥缺失或格式错误。

并发保护同时依赖事务行锁、条件更新、业务引用唯一约束和 `pending` 提现部分唯一索引。应用层预检查只用于更友好的错误提示，不能替代数据库约束。

## 11. 数据迁移

新增幂等迁移脚本，职责包括：

- 创建余额流水、用户收款码和提现申请表及索引。
- 插入默认最低提现金额设置，已有配置时不覆盖。
- 为每个当前余额大于 0 且尚无期初流水的用户插入一笔 `opening_balance` 流水，`amount` 和 `balance_after` 均为迁移时的当前余额。

迁移需要在单一事务中执行，并通过业务唯一键保证重复运行不会重复生成期初流水。

## 12. 测试与验收

### 12.1 后端测试

新增或扩展 `server/test/` 脚本，至少覆盖：

- 迁移首次执行和重复执行的幂等性。
- 期初余额生成规则。
- 微信、支付宝合法二维码解析。
- 无二维码、多二维码、错误平台、伪造文件和超大文件拒绝。
- 二维码加密、解密、篡改检测和密钥缺失行为。
- 最低提现金额默认值与管理员配置。
- 低于最低金额、余额不足、缺少收款码和已有处理中申请。
- 提现申请原子扣款、流水和收款码快照。
- 管理员确认不重复扣款。
- 管理员驳回退款、退款流水与驳回原因。
- 并发提交和并发处理只成功一次。
- 推广奖励同时增加余额并写入流水。
- 余额支付同时扣减余额并写入流水。
- 用户端和管理端查询、搜索、类型筛选及分页。

### 12.2 前端验证

- 构建 `client-user` 与 `client-admin`，确保无编译错误。
- 验证桌面端与移动端布局。
- 验证收款码上传、保存、更换、错误反馈和提现入口状态。
- 验证提现页金额校验、处理中状态、搜索、筛选和分页。
- 验证管理端列表、用户详情、二维码展示、确认和驳回交互。

### 12.3 完成标准

- 余额、流水和关联业务在成功路径及异常回滚后保持一致。
- 用户无法绕过最低金额、余额、收款码或单笔处理中申请限制。
- 管理员不会重复完成或重复退款。
- 数据库和日志中不存在二维码明文或原始上传图片。
- 两个前端均通过生产构建，相关后端测试脚本全部通过，并向用户展示测试日志。
- 因涉及 `server/**/*.js` 修改，交付时明确提醒用户重启服务器，但不代替用户启动服务。
