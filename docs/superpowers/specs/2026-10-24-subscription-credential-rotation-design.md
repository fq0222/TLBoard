# 用户订阅凭证轮换设计

## 背景与意图

现有“更换订阅链接”只更换 `users.sub_id`（网站对外公开的订阅 token），并把旧订阅缓存原样迁移到新 token。若用户的节点凭证已经泄露，旧的 `uuid/auth/password` 仍然可以继续连接 3X-UI 节点。

本次改造要让一次“更换订阅链接”同时完成公开 token 和各台 3X-UI 服务器客户端凭证的轮换。系统采用本地数据库为准、远端最终一致的方式：先可靠地保存新凭证，再分别同步各台服务器；单台服务器失败不得阻断其他服务器或让整个请求失败，并通过现有持久化任务队列继续补偿。

## 目标

- 用户点击一次后，更换网站公开订阅 token。
- 为该用户在每台启用的 3X-UI 服务器生成一套新的 `uuid/auth/password`；同一服务器的所有 inbound 共用这一套凭证。
- 新生成的三个非空凭证分别保证不与同一服务器内其他用户对应字段重复。
- 本地变更先提交，再同步到 3X-UI 3.4.2+。
- 各服务器独立同步；部分失败时仍返回新的公开订阅链接。
- 成功服务器使用新节点内容，失败服务器继续使用原订阅缓存中的节点。
- 失败服务器进入专用重试任务；每次重试读取数据库中的最新凭证，成功后重新生成订阅缓存。
- 每个用户 1 小时最多成功受理一次更换请求，限制在进程重启后仍然有效。

## 非目标

- 不更换节点级 `user_node_configs.sub_id`，因为它只用于本系统与对应 3X-UI 服务器之间获取原始订阅，没有向用户公开。
- 不兼容或改造 3X-UI 3.4.2 以下版本的凭证轮换流程；未来业务只使用 3.4.2 及以上版本。
- 不因远端失败回滚已经提交的公开 token 或本地新凭证。
- 不取消、合并或取代历史凭证轮换重试任务；不同任务可以继续存在，但都必须以执行时的最新本地凭证为准。
- 不修改购买、续费、启用、禁用等现有同步任务的业务语义。

## 约束与不允许出现的结果

- 不允许先改远端再写本地，避免请求中断后丢失远端真实凭证。
- 不允许某台服务器失败导致其他服务器停止同步。
- 不允许失败服务器因为本地凭证已更新而提前生成不可用的新节点。
- 不允许旧重试任务携带并重新写回历史凭证。
- 不允许并发请求绕过 1 小时限制。
- 不允许两个缓存重建任务互相覆盖，导致已成功服务器重新退回旧节点。
- 不允许复用现有会相互取代的普通 `user_sync` 任务类型。

## 已选方案

采用独立的凭证轮换编排服务和独立任务类型 `credential_rotation_sync`。一次任务携带待重试的服务器 ID 列表，而不是每台服务器创建一个任务。任务 payload 不保存 `uuid/auth/password`，执行时始终从本地数据库读取最新值。

### 考虑过的方案

1. **独立轮换任务（已选）**：与购买、续费同步隔离，能够清晰表达“同步成功才替换对应服务器缓存”的规则，也不会触发现有用户同步任务的相互取代逻辑。
2. **扩展现有 `user_sync`**：文件改动较少，但普通用户同步会复用或修正凭证，且 pending 用户同步任务会相互取代，容易破坏本次要求的历史任务互不影响。
3. **每台服务器一个任务**：服务器隔离最彻底，但会放大任务数量，并增加多个任务同时读写同一订阅缓存的竞争；单任务携带失败服务器列表已经能复用现有局部退避能力。

## 数据模型

### 用户更换时间

为 `users` 增加 `subscription_credentials_rotated_at BIGINT`，记录最近一次本地轮换事务成功提交的 Unix 秒时间戳。

请求处理时必须在专用 PostgreSQL 连接和事务内锁定用户记录（`SELECT ... FOR UPDATE`），再检查：

- 当前时间减去该字段小于 3600 秒：拒绝请求，返回 HTTP 429，并设置 `Retry-After` 为剩余秒数（向上取整且最少为 1）。
- 字段为空或已满 3600 秒：继续轮换，并在同一事务内更新时间。

远端部分失败不恢复时间戳，因为该次更换已经成功受理并提交了新公开 token 与新本地凭证。

### 服务器级凭证

继续使用 `user_node_configs` 保存凭证，不新增第二份凭证真相源。同一 `(user_id, server_id)` 下所有 inbound 行写入相同的 `uuid/password/auth`。3X-UI 3.4.2+ 的 client 是服务器级对象，因此同服务器各行必须共享同一个既有 `sub_id`，轮换过程不生成替代值。

目标服务器存在配置缺口时，以本地 `xui_nodes` 为 inbound 清单补齐 `user_node_configs`：

- 已有且一致的服务器级 `sub_id` 原样保留；同一服务器新增的缺失行复用该服务器已有的 canonical `sub_id`。
- canonical 行优先从本次 active inbound 的已有配置中选择；仅 active inbound 全部没有配置时才回退历史 inbound，避免失效的小 ID 历史行污染新补行。
- 若历史数据中同服务器存在多个不同 `sub_id`，不得选择首行静默覆盖远端；该服务器按同步失败处理，保留本地值与旧缓存并进入重试，等待独立的数据修复。
- 整台服务器没有任何用户配置时，生成一个新的内部 `sub_id` 并供该服务器所有新行共用；这属于初始化缺失配置，不属于更换已有 `sub_id`。
- 本地不存在该服务器可用的 inbound 快照时，第一阶段不凭空构造配置；该服务器保留原缓存并由轮换任务重试。重试获得有效快照后，仍须先把新配置提交到本地数据库，再写远端。

凭证生成和写入必须在同一个数据库事务中完成。事务按固定服务器 ID 顺序获取服务器级 PostgreSQL transaction advisory lock，避免两个轮换事务在同一服务器上同时执行“检查后写入”。每台服务器生成：

- `uuid`：`crypto.randomUUID()`。
- `password`：沿用当前 3X-UI 3.4.2+ 客户端密码生成规格，即 8 个随机字节的十六进制字符串。
- `auth`：沿用现有 `generateXuiAuth()` 规格。

每组候选值必须查询 `user_node_configs`，确认同一 `server_id` 下不存在其他 `user_id` 使用相同的非空对应字段；发生冲突时整组重新生成，直到通过检查。服务器级 advisory lock 和查询共同保证并发轮换不会写出重复值。已有通用 3X-UI 客户端创建路径也应复用同一套服务器级锁与唯一候选生成方法，避免另一类本地写入与轮换并发时绕过保证。

迁移和初始化表结构同步增加时间字段；无需修改 `sub_id` 或给重复的 inbound 行直接添加普通唯一索引，因为同一用户在同一服务器内本来就需要重复保存同一组凭证。

## 请求执行流程

### 第一阶段：本地原子轮换

`POST /api/user/subscription/replace-link` 保持原路径和鉴权方式。

编排服务在单个事务内完成：

1. 锁定并校验用户有效状态和 1 小时冷却时间。
2. 读取当前最新订阅缓存，保存为后续渐进更新的基线；没有缓存时仍按现有行为返回“请先生成订阅链接”。基线内每个真实节点必须包含有效 `server_id`；若存在无法归属服务器的历史节点，则拒绝本次轮换并提示用户先重新生成一次订阅，禁止按 `server_name` 或节点名称猜测归属。
3. 生成新的公开订阅 token，并处理极小概率的 token 唯一冲突。
4. 查询所有启用且面板版本不低于 3.4.2 的服务器，以及用户在这些服务器的 inbound 配置。
5. 按服务器生成并校验新 `uuid/auth/password`，批量更新该用户在该服务器的全部 `user_node_configs` 行；已有 `sub_id` 不变，历史不一致数据留到远端阶段安全失败。
6. 更新 `users.sub_id` 与 `subscription_credentials_rotated_at`。
7. 删除该用户旧 token 的 `user_subscriptions` 缓存，并用新 token 写入完全相同的旧节点基线，使新公开链接在远端同步开始前就可访问。
8. 在同一事务中创建一条 `credential_rotation_sync` pending 任务，payload 只包含 `user_id` 和本次全部目标 `serverIds`。
9. 提交事务。

任务与本地凭证在同一事务中落库，避免进程恰好在本地提交后、创建任务前退出而永久遗漏远端同步。如果任务创建失败，本地事务整体回滚，不开始任何远端同步，也不消耗 1 小时额度。

### 第二阶段：远端同步

事务提交后，对目标服务器使用现有受控并发能力执行同步。每台服务器的处理彼此隔离：

1. 读取该用户、该服务器当前最新的本地 `uuid/auth/password/sub_id`。
2. 通过 3X-UI 3.4.2+ 服务器级 client API，以用户 canonical email 更新客户端，并保持原有启用状态、到期时间、总流量等字段。
   - 每台服务器只对全部 inbound 做一次 server-level upsert，禁止逐 inbound 连续 update，因为后一次会覆盖同一 email client 的全局 `subId/flow`。
   - 本地 `sub_id` 不一致时不写远端；一致时使用该未变化的服务器级值。
   - 已存在的远端 client 原样保留其全局 `flow`。远端 client 缺失时，仅全 direct 节点初始化为 `xtls-rprx-vision`、全非 direct 不设置；混合策略无法由单一全局 `flow` 表达，按服务器失败进入重试。
3. 同步成功后，通过未更换的 `sub_id` 拉取该服务器最新原始订阅内容并刷新 `user_subscription_sources`。
4. 记录成功或失败服务器 ID；网络错误、查询错误、更新错误、原始订阅刷新错误都只标记当前服务器失败。

远端不得根据任务 payload 中的凭证写入，任务 payload 也不得包含这些敏感值。

该流程不能直接复用会在远端结果确定前调用 `clearSubscriptionSourceCache()` 的现有通用同步路径。凭证轮换必须保留旧 `user_subscription_sources`，直到对应服务器完成远端更新并成功拉取新来源后，再原子覆盖该服务器的来源记录；远端失败时旧来源和旧最终节点缓存都保持不变。

### 第三阶段：渐进重建订阅缓存

远端一轮执行完成后，使用用户级 advisory lock 串行化缓存重建：

1. 重新读取用户当前 `sub_id`，绝不使用任务创建时的公开 token。
2. 读取当前全部 `user_subscription_sources`：成功服务器已经是新来源，失败服务器仍保留旧来源。
3. 重新组合全部节点、CF 优选和节点命名信息，并写入当前 token 对应的 `user_subscriptions`。
4. 因此成功服务器切换到新凭证，失败服务器节点不删除、不隐藏、不改写，继续沿用原缓存内容。

为了严格保留失败服务器原缓存，合并单位使用缓存节点中的 `server_id`：本轮成功服务器的节点集合替换原缓存中相同 `server_id` 的节点；其他服务器节点直接保留原值。这样即使失败服务器的来源缓存存在其他后台刷新，也不会被本次凭证轮换误改。

若成功服务器的新节点生成失败，则把该服务器视为本轮失败，保留原缓存并进入重试。

## 重试任务

在 `xui_sync_tasks` 中新增 `credential_rotation_sync` 类型，但不把它加入会被 `supersedePendingUserSyncTasks()` 取代的 `USER_SYNC_TASK_TYPES`。

本地事务提交后，HTTP 请求立即调用 `processTask()` 处理刚创建的任务并等待这一轮全部目标服务器返回。首次远端处理结束后：

- 全部成功：任务标记成功；不安排重试。
- 部分或全部失败：任务 payload 只保存 `user_id` 和去重后的 `serverIds`，使用现有退避规则进入 pending。
- HTTP 请求仍返回成功和新订阅链接，可附带 `pending_server_ids`/`pending_server_names` 供前端提示，但不得因为这些服务器失败返回整体错误。

worker 每次执行：

1. 根据 `user_id` 读取最新用户记录。
2. 根据 `serverIds` 读取各服务器最新 `user_node_configs` 凭证。
3. 只同步任务记录的失败服务器。
4. 对本轮成功服务器执行来源刷新和渐进缓存替换。
5. 仍失败的服务器 ID 作为下一轮缩小后的 payload。
6. 即使最终达到最大尝试次数，也保留当前缓存；已成功服务器的更新不会回滚。

多个历史轮换任务可以并存。由于它们都读取最新本地凭证、使用最新公开 token，并在用户级缓存锁内进行按服务器合并，因此旧任务不会恢复旧凭证或旧 token；重复同步最新值是幂等操作。

## API 与前端行为

成功响应继续包含 `subscription_url`、`clash_url` 和 `v2ray_url`，保持现有前端兼容。可增加：

- `pending_server_ids`：等待后台补偿的服务器 ID。
- `pending_server_names`：用于用户提示的服务器名称。
- `retry_scheduled`：是否已成功写入补偿任务。

只要本地事务成功，远端部分失败仍返回业务成功。若补偿任务本身无法持久化，则记录严重错误，并在响应中明确提示后台补偿未建立；不能谎报已安排重试。

冷却命中返回 HTTP 429，业务消息说明 1 小时只能更换一次，并带标准 `Retry-After`。前端展示服务端消息即可。更换中的弹窗文案应说明系统同时更新节点凭证；完成提示在存在 pending 服务器时说明部分节点将在后台完成更新，但新链接已经可用。

## 并发与一致性

- 用户行 `FOR UPDATE`：保证同一用户的两个请求无法同时通过 1 小时检查。
- 固定顺序的服务器级 transaction advisory lock：保证同服务器候选凭证的检查与写入串行，避免死锁和并发重复。
- 现有 `(server_id, canonical email)` 远端 advisory lock：继续保护同一 3X-UI 客户端的远端查询与更新。
- 用户级缓存 advisory lock：保证多个轮换重试、订阅来源补偿或后续再次更换不会发生缓存读改写丢失。
- 所有后台任务在写缓存前重新读取 `users.sub_id`；第二次合法更换发生后，旧任务只能更新最新 token 的缓存，不会复活旧链接。

## 错误处理与日志

- 日志记录用户 ID、服务器 ID/名称、任务 ID、阶段、错误类型和重试次数。
- 日志不得输出公开 token、`sub_id`、`uuid`、`auth`、`password` 或包含这些值的完整远端 URL。
- 服务器级结果区分：远端同步失败、原始订阅拉取失败、节点生成失败、缓存写入失败。
- 缓存写入失败属于可重试失败；远端已成功时下一轮重复写入相同最新凭证是安全的。

## 测试与验收

后端测试至少覆盖：

- 本地事务一次更新公开 token、轮换每台服务器凭证、保留一致的服务器级 `sub_id`，并让同服务器所有 inbound 使用同一套凭证；历史不一致 `sub_id` 不被静默覆盖。
- 候选凭证与同服务器其他用户冲突时重新生成；其他服务器相同值不构成冲突。
- 两个并发请求只有一个成功，另一个返回 429；数据库失败不消耗冷却时间。
- 冷却剩余时间正确写入 `Retry-After`，满 3600 秒后允许再次更换。
- 一台成功、一台失败时：成功服务器缓存换新，失败服务器缓存逐项保持原值，请求仍成功并只把失败服务器入队。
- 全部失败时：新公开 token 生效，但全部节点仍是旧缓存，所有失败服务器入队。
- 重试执行时读取数据库最新凭证，而不是任务创建时的值。
- 多个历史任务依次或并发执行不会复活旧公开 token、旧凭证或覆盖其他服务器已更新的缓存。
- 重试部分成功后立即重建当前 token 的缓存，并仅保留仍失败服务器到下一轮。
- 任务达到最大次数后不删除现有节点缓存。
- 日志和任务 payload 不泄露敏感凭证。
- 3X-UI 3.4.2 以下服务器不进入本流程，并留下清晰告警或配置错误记录。
- 缺少部分节点配置时按 `xui_nodes` 补齐并复用服务器原 `sub_id`；整台服务器无配置时生成一个内部 `sub_id`。
- 本地无 inbound 快照时不构造远端配置，保留缓存并等待重试；重试时仍验证本地先于远端落库。
- 历史缓存存在缺失或无效 `server_id` 的真实节点时拒绝轮换，且不消耗冷却时间。

前端执行生产构建；后端运行相关新增测试以及现有 `server/test/test-user-subscription-service.js`、3X-UI 同步队列和 3.4.2 client 同步测试。实现完成时展示完整测试日志。由于会修改 `server/**/*.js`，交付时提醒用户重启服务器，但不自行启动。

## 实施边界

实现者可以决定新类和仓储方法的具体命名，但应遵守项目规则：包含多个方法和内部状态的编排模块使用 `class` 封装；新增文件和方法补充职责、关键参数和核心分支注释。尽量复用现有并发执行器、XUI 服务、来源刷新、节点组合和任务退避逻辑，不改写无关订阅生成流程。
