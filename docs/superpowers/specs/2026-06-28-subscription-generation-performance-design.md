# 用户订阅生成性能优化设计

## 背景

用户首次生成订阅时，当前实现会依次完成两轮远程访问：

1. 遍历所有在线 3X-UI 服务器并获取完整 inbound 列表。
2. 遍历用户节点配置并逐个拉取原始订阅模板。

这两轮请求目前主要按顺序执行。生产环境服务器较多或晚间网络拥塞时，请求耗时会累加，可能超过前端 120 秒超时并导致生成失败。

项目已有 3X-UI 用户同步巡检任务：服务启动一分钟后执行一次，之后每四小时执行一次。该任务会刷新 `xui_nodes` 快照并维护 `user_node_configs`。购买同步成功后，用户通常已经拥有各节点对应的 UUID 和独立 `sub_id`，因此首次生成无需无条件重新获取所有服务器的 inbound。

## 目标

- 用户完成购买后，生成订阅必须在当前请求内完成，不能依赖后台任务稍后补齐。
- 正常情况下优先使用本地节点快照和用户节点配置，避免全量获取 inbound。
- 本地配置不完整时，只同步存在缺口的服务器。
- inbound 请求和原始订阅请求均使用限流并发，最大并发数为 10。
- 获取 inbound 的单请求超时为 10 秒。
- 获取原始订阅的单请求超时为 5 秒。
- 单台服务器或单个节点失败时不终止整批生成；记录日志并继续处理其他节点。
- 最终至少生成一个可用节点即返回成功；没有任何可用节点时返回失败。

## 非目标与一致性边界

- 首次生成不保证发现定时巡检之后刚在 3X-UI 新增、但尚未进入本地 `xui_nodes` 的 inbound。
- 上述情况不会阻止用户使用本地已知且生成成功的节点，新 inbound 会在后续巡检或定向修复后出现。
- 本次优化不调整定时任务的执行频率。
- 本次优化不把订阅生成改成异步任务，也不改变订阅链接格式。

## 总体方案

采用“本地快速路径、缺口定向同步、两阶段限流并发、失败隔离”的生成流程。

### 第一阶段：判断本地配置完整性

读取以下本地数据：

- 当前在线服务器；
- 在线服务器对应的 `xui_nodes` 快照；
- 当前用户的 `user_node_configs`。

使用 `server_id + inbound_id` 作为节点唯一匹配键。逐台服务器比较本地节点快照与用户节点配置：

- 如果该服务器所有本地节点均有用户配置，则认为本地配置完整，跳过该服务器的远程 `getInbounds()`。
- 如果服务器没有本地节点快照，或存在任一节点缺少用户配置，则把该服务器加入待同步集合。

判断依据使用结构化的 `user_node_configs`，不依赖 `xui_nodes.settings` 中可能陈旧的客户端列表。

### 第二阶段：定向同步缺口服务器

仅对待同步集合中的服务器获取 inbound：

- 最大并发数：10；
- 单请求超时：10 秒；
- 使用全部结果收集语义，单台失败不抛弃其他服务器的成功结果；
- 成功后刷新该服务器的 `xui_nodes` 快照；
- 根据最新节点快照补齐当前用户的 `user_node_configs`；
- 失败时记录服务器 ID、名称、耗时和错误原因，继续生成其他服务器的节点。

现有 `getInbounds()` 是服务器级接口，一次返回该服务器的全部 inbound。因此优化粒度是“跳过或同步整台服务器”，不是跳过某个单独 inbound。

### 第三阶段：并发刷新原始订阅模板

基于当前可用的用户节点配置拉取原始订阅：

- 最大并发数：10；
- 单请求超时：5 秒；
- 每个节点使用其独立 `sub_id` 请求所属服务器的 `sub_url`；
- 成功解析出与节点协议匹配的链接后，写入原始模板缓存；
- 单节点超时、网络错误或没有匹配链接时记录警告，并继续处理其他节点；
- 如果已有与当前 `sub_id`、节点指纹和服务器指纹匹配的缓存，可以继续复用该缓存。

### 第四阶段：定向修复失败节点

首次快速拉取失败时，按失败节点的 `server_id` 去重：

1. 仅对失败节点所属服务器执行并发 `getInbounds()`。
2. 刷新这些服务器的节点快照并修复用户节点配置。
3. 仅重试受影响节点的原始订阅拉取，不重复请求已经成功的节点。

定向修复仍遵守 inbound 并发 10、超时 10 秒，以及原始订阅并发 10、超时 5 秒。每个生成请求最多执行一轮定向修复，避免异常服务器反复延长用户等待时间。

## 数据流

```text
用户点击生成
  -> 校验用户、套餐、CF IP 和在线服务器
  -> 对比 xui_nodes 与 user_node_configs
  -> 并发同步存在配置缺口的服务器
  -> 补齐用户节点配置
  -> 并发拉取原始订阅模板
  -> 对失败节点执行一次定向同步与重试
  -> 使用成功模板按 CF/direct 策略拼装节点
  -> 保存 user_subscriptions 缓存
  -> 返回通用、Clash 和 V2Ray 订阅链接
```

## 并发控制

新增通用的限流并发执行能力，调用方传入任务列表、并发上限和单任务处理函数。该能力应满足：

- 同时运行的任务不超过指定上限；
- 返回结果保持与输入任务可关联；
- 单任务失败被转换为失败结果，不提前终止任务池；
- 不使用无上限 `Promise.all()`；
- 并发工具与订阅业务解耦，并补充职责、参数和失败语义注释。

订阅模块使用以下常量，后续可按需要迁移到配置文件：

```text
INBOUND_SYNC_CONCURRENCY = 10
INBOUND_REQUEST_TIMEOUT_MS = 10000
SOURCE_FETCH_CONCURRENCY = 10
SOURCE_FETCH_TIMEOUT_MS = 5000
```

超时必须落实到实际 HTTP 请求，而不只是外层 Promise 计时，以便及时释放 Axios 请求资源。

## 错误处理

### 可以降级成功

- 部分服务器获取 inbound 失败；
- 部分服务器没有本地节点；
- 部分原始订阅请求超时或解析失败；
- 定向修复后仍有少量节点失败。

只要最终至少生成一个有效节点，接口返回成功并保存成功节点。

### 必须返回失败

- 没有在线服务器；
- 用户未完成 CF IP 优选；
- 本地快速路径、定向同步和一次定向修复后仍没有任何有效节点；
- 用户、套餐或账号状态不允许生成订阅。

## 日志

每次生成至少输出以下汇总日志：

- 本地快速路径命中的服务器数；
- 需要远程同步的服务器数；
- inbound 同步成功数、失败数和总耗时；
- 原始模板拉取成功数、失败数和总耗时；
- 定向修复涉及的服务器数和节点数；
- 最终生成节点数和总耗时。

单项失败日志包含：

- 用户标识；
- 服务器 ID 和名称；
- inbound ID（适用时）；
- 请求耗时；
- 错误类型：超时、网络错误、响应异常、缺少匹配链接或配置不完整。

日志不得输出 API Token、完整 UUID、完整 `sub_id` 或订阅内容。

## 测试与验证

### 自动化测试

- 本地快照和用户配置完整时，不调用远程 `getInbounds()`。
- 缺少部分用户节点配置时，只同步对应服务器。
- 超过 10 台服务器时，inbound 最大并发数不超过 10。
- 超过 10 个节点时，原始订阅最大并发数不超过 10。
- inbound 请求在 10 秒超时后被标记失败，其他任务继续。
- 原始订阅请求在 5 秒超时后被标记失败，其他任务继续。
- 部分服务器失败但存在成功节点时，接口生成成功。
- 所有节点失败时，接口返回明确失败。
- 原始模板首次失败后，只对失败服务器执行一次定向修复。
- 有效旧缓存存在时能够安全复用，不匹配当前 `sub_id` 或指纹的缓存不得复用。

### 项目验证

按照项目规范运行 `server/test/` 下与订阅、3X-UI 同步相关的脚本，并保留完整测试日志。由于会修改 `server/**/*.js`，实施完成后提醒用户重启服务器，但不自行启动服务器。

## 风险与控制

- **快照过期遗漏新 inbound**：接受最多一个定时巡检周期内无法发现新 inbound 的一致性边界。
- **并发造成瞬时压力**：两个阶段分别限制最大并发为 10，不叠加成无上限任务。
- **部分成功导致节点较少**：日志明确记录失败对象，用户仍可立即使用成功节点。
- **失败重试拉长耗时**：仅失败节点执行一次定向修复，不进行循环重试。
- **陈旧配置生成错误链接**：原始模板必须与当前 `sub_id`、节点指纹和服务器指纹匹配；不匹配则刷新或跳过。
