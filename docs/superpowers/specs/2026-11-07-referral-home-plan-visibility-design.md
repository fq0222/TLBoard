# 推广首页套餐展示设计

## 意图

在管理端套餐编辑弹窗中新增“推广首页展示”开关。管理员可以让套餐仅在有效推广链接进入的首页展示，同时保留现有“首页展示”开关的全量首页展示语义。

## 展示规则

套餐仍须处于已上架状态。满足上架条件后，按以下规则决定首页可见性：

| 访问场景 | `show_on_home` | `show_on_referral_home` | 结果 |
| --- | ---: | ---: | --- |
| 普通首页、缺少 `ref`、无效或已禁用的 `ref` | 1 | 任意 | 展示 |
| 普通首页、缺少 `ref`、无效或已禁用的 `ref` | 0 | 1 | 隐藏 |
| 有效推广链接 | 1 | 任意 | 展示 |
| 有效推广链接 | 0 | 1 | 展示 |
| 任意访问场景 | 0 | 0 | 隐藏 |

有效推广链接以当前首页 URL 中的 `ref` 查询参数为准；对应推广码必须存在于 `referral_codes` 表且 `enabled = 1`。会话中曾缓存过推广码但当前 URL 不含 `ref` 时，不触发推广首页套餐展示。

## 数据与接口设计

- `plans` 表新增整数布尔字段 `show_on_referral_home`，默认值为 `0`，历史套餐迁移后保持关闭，避免上线后意外扩大展示范围。
- 管理端套餐列表、创建和更新接口读写该字段；路由层校验其为布尔值，服务层统一转换为数据库的 `0/1`。
- 用户端 `GET /api/user/plans` 新增可选查询参数 `ref`。
- 后端先判断 `ref` 是否对应启用中的推广码，再选择套餐过滤条件：
  - 有效 `ref`：`enabled = 1 AND (show_on_home = 1 OR show_on_referral_home = 1)`；
  - 其他情况：`enabled = 1 AND show_on_home = 1`。
- 无效推广码不报错，按普通首页处理，避免链接输错导致整个套餐列表加载失败。
- 续费页套餐查询不受两个首页展示开关影响，保持现有行为。

## 前端设计

- 管理端套餐编辑/新增弹窗在“首页展示”和“是否上架”之间增加“推广首页展示”开关，默认关闭。
- 编辑套餐时将数据库返回的 `0/1` 转为布尔值；提交时随套餐表单一并发送。
- 管理端桌面套餐列表增加推广展示状态，移动端套餐卡片同步展示两个首页可见性状态，便于管理员核对。
- 用户首页加载套餐时，仅把当前路由的 `ref` 参数传给套餐接口。现有推广码缓存与点击上报继续保留，二者与套餐查询相互独立。

## 安全与兼容性

- 推广码有效性只能由后端数据库校验，前端不能直接声明推广访问有效。
- 查询参数只用于可见性筛选，不返回推广人身份等额外信息。
- 新字段默认关闭，旧客户端不提交该字段时，新增和更新接口仍有明确默认值或保持原值。
- 两个开关都打开时，“首页展示”的全量可见语义自然覆盖推广场景，不产生冲突。

## 方案取舍

1. **采用：套餐接口接收 `ref`，后端统一校验和筛选。** 判断集中、不可由前端伪造，且一次套餐请求即可得到正确结果。
2. 未采用：前端先调用推广点击接口，再根据响应加载套餐。该方案需要串行请求，失败和重试状态更复杂，并把展示规则分散到前端。
3. 未采用：把两个开关合并为单个“展示范围”枚举。数据更集中，但不符合两个独立开关的管理需求，迁移和界面改动也更大。

## 验证范围

- 后端测试覆盖普通访问、有效推广码、无效推广码、已禁用推广码，以及两个开关的组合结果。
- 后端管理套餐测试覆盖新字段的创建、更新、缺省值和格式化输出。
- 用户端测试覆盖首页把当前 `ref` 传给套餐接口，无 `ref` 时不传推广参数。
- 管理端测试覆盖新增/编辑表单的默认值、布尔转换与提交字段。
- 最终运行相关 `server/test/` 脚本，并分别执行 `client-user`、`client-admin` 生产构建；实施完成时展示完整验证日志。

## 非目标

- 不改变推广奖励、注册归因、推广点击统计或推广码生成规则。
- 不让“推广首页展示”影响登录后的续费套餐列表。
- 不调整首页套餐卡片样式、排序规则或售罄判断。
