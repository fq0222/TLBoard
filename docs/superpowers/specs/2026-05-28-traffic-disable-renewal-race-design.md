# 流量禁用与续费解禁竞态修复设计

> 日期：2026-05-28
> 状态：待评审
> 范围：修复“流量超限自动禁用”和“用户续费后自动解禁”之间的竞态问题，并收口相关重复同步入口

## 一、问题定义

### 1.1 现象

当前系统中，存在两条会修改用户启用状态并同步到 3X-UI 的路径：

1. 续费成功后，用户应恢复为启用状态，并同步解禁到 3X-UI
2. 流量同步任务发现用户超限后，会禁用本地用户，并同步禁用到 3X-UI

当这两条路径几乎同时处理同一个用户时，可能出现竞态：

1. 流量任务基于旧快照判断用户已超限
2. 用户在此时完成续费，本地 `traffic_limit` 增大，且应恢复启用
3. 流量任务继续使用旧结论执行禁用
4. 刚续费的用户被重新禁用

### 1.2 本次设计目标

本设计只解决以下问题：

1. 修复续费后解禁逻辑的错误判断
2. 防止流量任务基于旧快照误禁用刚续费的用户
3. 串行化同一用户的“禁用/解禁状态迁移”
4. 收口与本问题直接相关的重复同步入口，避免后续逻辑再分叉

本设计不包含以下内容：

1. 不重写整个流量同步架构
2. 不调整套餐、订单、订阅规则
3. 不改前端页面和交互
4. 不顺带做与本问题无关的大规模重构

---

## 二、现状与根因

### 2.1 续费解禁逻辑存在死判断

在 `server/services/order-service.js` 的 `completePaidOrder()` 中，续费事务会把用户更新为 `enabled = 1`。

但事务完成后，代码又重新查询 `users.enabled`，并使用“当前是否为 0”来决定是否执行解禁同步。

这会导致：

1. 续费前本来是禁用用户
2. 事务里已经改成 `enabled = 1`
3. 事务后重新查询到的也是 `1`
4. 解禁分支不成立，`syncDisableStatusToXui(..., false)` 不执行

因此，续费后的 3X-UI 解禁同步在当前实现中存在明显漏执行风险。

### 2.2 流量禁用逻辑使用了旧结论

在 `server/services/traffic-manager.js` 中：

1. `calculateUserTotalTraffic()` 会基于某个时间点的用户数据计算 `isOverLimit`
2. `updateTrafficInDatabase()` 先写回 `traffic_used`
3. `checkAndDisableOverLimitUsers()` 再根据先前计算好的 `data.isOverLimit` 决定是否禁用

但真正禁用前，当前实现只重新读取了：

1. `enabled`

没有重新读取并重新判断：

1. `traffic_used`
2. `traffic_limit`
3. 用户是否已经因续费恢复

所以流量任务可能在“计算时超限、执行时已不超限”的情况下，仍然继续禁用。

### 2.3 状态迁移缺少统一互斥

当前“续费解禁”和“超限禁用”虽然最终都影响同一个用户的 `enabled` 状态，但并没有共享同一个串行化机制。

这意味着：

1. 两条路径都可能同时对同一用户发起 3X-UI 外部调用
2. 两条路径都可能在外部调用完成后回写本地状态
3. 最终结果受执行时序影响，而不是受最新数据库状态约束

### 2.4 相关入口存在重复定义风险

当前与本问题直接相关的状态同步入口存在重复实现或分散调用的问题，尤其是：

1. `server/services/order-service.js`
2. `server/jobs/index.js`

如果本次修复只改其中一处，后续仍可能有旧入口绕过新规则。

## 三、设计目标

### 3.1 功能目标

1. 续费前已禁用的用户，在续费后一定会触发解禁同步
2. 流量任务在真正禁用前，必须基于最新数据库状态重新判断是否仍超限
3. 同一用户的“禁用/解禁状态迁移”必须串行执行
4. 锁获取失败时不阻塞等待，但不能直接丢弃状态同步
5. 订单侧和任务侧都走同一套状态迁移规则

### 3.2 非功能目标

1. 保持支付事务与外部 3X-UI 调用解耦
2. 不因为锁竞争导致支付成功回滚
3. 在多任务并发场景下保持可重试性
4. 改动面尽量集中在服务层，避免扩散到前端和路由层

---

## 四、方案对比

### 方案 1：只修续费解禁死代码

做法：

1. 查询订单时带出续费前 `enabled`
2. 用续费前状态决定是否执行解禁同步

优点：

1. 改动最小
2. 能修复“续费后没解禁”的明显 bug

缺点：

1. 不能阻止流量任务用旧快照重新禁用用户
2. 不能解决并发状态覆盖

结论：不够。

### 方案 2：修死代码 + 禁用前二次校验

做法：

1. 包含方案 1
2. 流量任务禁用前重新查询最新状态并重新计算是否超限

优点：

1. 能解决大部分误禁用
2. 改动仍较集中

缺点：

1. 续费解禁和流量禁用仍可能在外部调用阶段交错

结论：可用，但不够稳。

### 方案 3：修死代码 + 二次校验 + 用户级锁 + 收口入口

做法：

1. 包含方案 2
2. 新增 `userId` 级 PostgreSQL advisory lock
3. 续费解禁与超限禁用共享同一把锁
4. 收口与本问题相关的重复同步入口

优点：

1. 同时解决业务判断错误和并发覆盖
2. 语义清晰，锁粒度与问题本质一致
3. 能覆盖支付同步、定时任务、重试任务和未来多实例

缺点：

1. 改动比方案 2 稍大
2. 需要补测试覆盖锁竞争与重试语义

结论：推荐采用本方案。

## 五、详细设计

### 5.1 续费流程改造

文件：

1. `server/services/order-service.js`

`completePaidOrder()` 在查询订单和用户时，新增读取续费前状态，例如：

1. `u.enabled as current_enabled`

后续逻辑改为：

1. 事务内继续按现有业务规则更新 `expire_at`、`traffic_limit`、`enabled`
2. 事务完成后，不再重新查询“现在是不是禁用”
3. 而是用“续费前是否禁用”来决定是否需要发起解禁同步

目标语义：

1. 续费前禁用过，续费后就要触发解禁同步
2. 不再依赖事务后查询到的最新 `enabled` 值做判断

### 5.2 流量禁用前的二次校验

文件：

1. `server/services/traffic-manager.js`

`checkAndDisableOverLimitUsers()` 改为两阶段判断：

1. 第一阶段继续使用 `calculateUserTotalTraffic()` 产出的结果做候选筛选
2. 第二阶段在真正禁用前，重新查询该用户最新数据库状态：
   - `enabled`
   - `traffic_used`
   - `traffic_limit`

然后基于最新数据库值重新计算：

1. 当前是否仍超限
2. 当前是否仍处于启用状态

只有在“当前仍超限且当前仍启用”时，才允许继续执行 3X-UI 禁用同步和本地禁用落库。

### 5.3 共享用户状态锁

文件：

1. `server/services/traffic-manager.js`
2. 如有必要，可提取到新的公共辅助文件，例如 `server/services/user-status-lock.js`

新增共享辅助方法，例如：

1. `buildUserStatusLockKey(userId)`
2. `withUserStatusLock(db, userId, fn, options = {})`

锁实现建议：

1. 使用 PostgreSQL advisory lock
2. 锁粒度为 `userId`
3. 使用非阻塞获取方式，例如 `pg_try_advisory_lock`

选择 `userId` 粒度的原因：

1. 本次冲突的对象不是某个 inbound，而是用户启用状态
2. 同一个用户的禁用和解禁必须串行
3. 不同用户之间不需要互相阻塞

### 5.4 锁竞争时的处理策略

锁获取失败时，不采用阻塞等待。

原因：

1. 3X-UI 是外部调用，耗时不可控
2. 阻塞等待会拖长定时任务执行时间
3. 支付流程不应被长时间卡住

锁获取失败后的处理语义如下：

#### 续费路径

1. 本地支付结果和续费权益更新照常成功
2. 若解禁同步拿不到锁，不回滚支付结果
3. 将本次 3X-UI 解禁视为可补偿失败，进入现有重试机制

#### 流量任务路径

1. 若禁用同步拿不到锁，本次不继续执行禁用
2. 记录日志并返回可重试结果
3. 由下一轮任务或重试机制继续处理

这意味着：

1. 第二个竞争任务不会自动等待前一个任务完成后继续执行
2. 但也不会被永久抛弃
3. 正确行为是“本次放弃执行，后续重试”

### 5.5 本地状态与 3X-UI 同步顺序

禁用路径建议保持以下顺序：

1. 拿用户状态锁
2. 读取最新数据库状态并确认仍需禁用
3. 调用 `syncDisableStatusToXui(db, userId, true)`
4. 3X-UI 禁用成功后，再更新本地 `enabled = 0`

解禁路径建议保持以下顺序：

1. 本地续费事务先成功提交
2. 若续费前为禁用状态，则尝试拿用户状态锁
3. 调用 `syncDisableStatusToXui(db, userId, false)`
4. 若同步失败，则走补偿逻辑，不回滚续费事务

注意：

1. 不要求把支付事务和外部调用合并到一个数据库事务内
2. 支付落账与状态同步仍应分层处理

### 5.6 收口重复入口

文件：

1. `server/services/order-service.js`
2. `server/jobs/index.js`

本次需要顺手收口与状态同步直接相关的重复定义，原则如下：

1. 同一职责只保留一个真实执行入口
2. 旧的重复实现移除或改为复用统一入口
3. 避免某些调用方继续走旧逻辑，绕过新锁和二次校验

这里的目标不是大规模重构，而是消除“本问题修了一处、另一处仍绕过”的风险。

## 六、流程

```text
续费成功
  -> completePaidOrder 查询订单 + current_enabled
  -> 本地事务提交续费权益
  -> 如果 current_enabled = 0
     -> 尝试获取 userId 锁
     -> 成功：同步 3X-UI 解禁
     -> 失败：记录可补偿失败，交给重试机制

流量同步任务
  -> calculateUserTotalTraffic 产出候选超限用户
  -> updateTrafficInDatabase 更新流量
  -> checkAndDisableOverLimitUsers 逐个处理候选
     -> 尝试获取 userId 锁
     -> 成功：重新查询 enabled/traffic_used/traffic_limit
     -> 若仍超限且仍启用：同步 3X-UI 禁用，再更新本地 enabled = 0
     -> 若已不超限或已禁用：跳过
     -> 失败：记录可重试结果，等待下轮处理
```

## 八、测试设计

### 8.1 必测场景

1. 续费前已禁用的用户，续费后会触发解禁同步
2. 续费前未禁用的用户，续费后不会多做一次无意义解禁
3. 流量任务拿到旧快照，但禁用前发现用户已续费恢复，不再禁用
4. 真正超限且仍启用的用户，仍会正常禁用
5. 同一用户“续费解禁”和“流量禁用”并发时，最终状态以最新数据库状态为准
6. 锁获取失败时：
   - 支付路径不回滚续费结果
   - 流量路径返回可重试结果
7. 收口重复定义后，原有相关同步流程不回归

### 8.2 验证方式

优先使用脚本测试和假服务桩验证：

1. 本地数据库状态变化
2. 3X-UI 同步函数调用顺序
3. 锁竞争下的返回结果
4. 最终用户 `enabled`、`traffic_used_at`、`traffic_limit` 是否符合预期

## 九、风险与边界

### 9.1 风险

1. 如果锁范围过大，可能让任务吞吐下降
2. 如果锁范围过小，仍可能残留状态覆盖
3. 如果续费路径把“同步失败”当成致命错误，可能影响支付结果落账
4. 如果只修业务判断、不收口旧入口，后续仍可能被旧逻辑绕过

### 9.2 风险控制

1. 锁粒度限定为 `userId`
2. 锁策略采用非阻塞获取，避免任务长时间卡住
3. 支付事务与 3X-UI 外部同步分离
4. 对锁获取失败、二次校验跳过、真正禁用/解禁都补结构化日志

---

## 十、预期结果

实施完成后，应达到以下效果：

1. 续费后不会因为错误判断漏掉解禁同步
2. 流量任务不会再基于旧快照把刚续费的用户重新禁掉
3. 同一用户的禁用/解禁状态迁移在多入口下保持串行
4. 锁竞争不会导致支付结果回滚，也不会导致状态同步被永久丢弃
5. 与本问题相关的同步入口不再分叉绕过修复逻辑
