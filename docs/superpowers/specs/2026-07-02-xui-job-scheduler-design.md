# 3X-UI 定时任务统一调度设计

## 背景

项目中的 3X-UI 用户同步、流量同步和 Telegram 健康巡检均会访问 3X-UI 服务器，但当前分别通过独立的 `setTimeout` 和 `setInterval` 触发。任务执行耗时不固定，因此即使首次触发时间已经错开，后续仍可能在同一时间段执行，造成 3X-UI 请求集中爆发。

## 目标

- 三个受控任务不能交叉执行。
- 上一个受控任务实际结束后，至少等待 5 分钟才能启动下一个受控任务。
- 同名任务在运行中或排队时再次触发，只保留一次执行机会。
- 保持各任务现有的首次延迟和执行周期不变。
- 单个任务失败不能阻塞后续任务。

## 范围

纳入统一调度：

- 3X-UI 用户同步。
- 流量同步。
- Telegram 健康巡检。

不纳入统一调度：

- 3X-UI 同步重试队列。
- 3X-UI 数据库备份。
- 批量订阅生成及恢复任务。
- 其他不访问 3X-UI 的后台任务。

## 方案选择

采用单进程内的统一 FIFO 调度器。

仅调整三个任务的触发时间不能保证长时间运行后仍不重叠；PostgreSQL 分布式锁可以支持多进程协调，但当前项目采用单实例任务调度，不需要引入数据库状态和额外恢复逻辑。进程内调度器是满足当前需求的最小可靠方案。

如果未来在多个 Node.js 进程中同时注册定时任务，应将调度状态升级为 PostgreSQL advisory lock 和持久化结束时间；本次不实现该扩展。

## 调度器设计

新增 `server/jobs/xui-job-scheduler.js`，对外提供以下职责：

- 接收任务名称和异步执行函数。
- 维护一个 FIFO 待执行队列。
- 维护正在运行的任务和已排队任务名称。
- 记录上一个受控任务的实际结束时间。
- 在执行下一项前计算剩余冷却时间。
- 停止时取消冷却计时并清空待执行队列。

建议接口：

```javascript
xuiJobScheduler.schedule(taskName, handler)
xuiJobScheduler.stop()
```

任务名称使用稳定常量：

- `xui-user-sync`
- `traffic-sync`
- `telegram-health-check`

## 调度规则

1. 第一个进入空闲调度器的任务可以立即执行。
2. 任务运行期间，其他受控任务只能进入队列。
3. 任务结束后记录 `lastFinishedAt`，无论该任务成功还是失败。
4. 下一项必须等到 `lastFinishedAt + 5 分钟` 后启动。
5. 队列按首次触发顺序执行，不设置额外优先级。
6. 某任务已经运行或已经排队时，同名触发不再新增队列项。
7. 同名合并只覆盖当前运行或排队周期；该任务完成并移出调度状态后，新的触发可以再次入队。
8. 任务抛出异常时记录失败日志，释放运行状态，并在冷却期后继续处理下一项。

## 接入方式

保留三个 handler 原有的首次延迟和执行周期，只将实际业务调用包装为调度请求：

```javascript
xuiJobScheduler.schedule('traffic-sync', async () => {
  await trafficManager.syncTrafficAndHandleDisable(db);
});
```

3X-UI 用户同步和 Telegram 健康巡检采用相同方式接入。现有任务内部的日志、业务异常处理和防重入保护可以保留；统一调度器只负责跨任务互斥、冷却和同名合并。

`server/jobs/index.js` 的 `stopAllJobs()` 在清理 interval、timeout 和 cron 后调用调度器的 `stop()`，避免应用停止后仍有冷却定时器触发任务。

## 日志

调度器记录以下关键事件：

- 任务进入队列及当前队列长度。
- 同名任务被合并。
- 任务因冷却期等待及剩余等待时间。
- 任务开始。
- 任务结束、执行状态和耗时。
- 调度器停止及丢弃的待执行任务数量。

日志不记录 3X-UI Token 等敏感信息。

## 测试

新增后端测试脚本，使用可控的短冷却时间或时间依赖注入验证：

1. 两个不同任务不会并发执行。
2. 下一任务在上一任务结束并经过完整冷却期后才开始。
3. 同名任务在运行中重复触发时只执行一次。
4. 同名任务在排队时重复触发时只保留一个队列项。
5. 一个任务抛出异常后，后续任务仍能执行。
6. 调度器停止后不会执行尚未开始的任务。

实现完成后运行新增测试脚本，并运行与三个接入任务相关的现有后端测试。

## 非目标

- 不改变三个任务的执行频率。
- 不限制用户请求、管理端操作或同步重试队列对 3X-UI 的访问。
- 不实现任务持久化、进程重启后恢复队列或跨进程互斥。
- 不为调度器引入第三方队列依赖。

## Class 结构补充

调度器使用 `XuiJobScheduler` class 封装内部状态和行为：

- `queue`、`scheduledNames`、`runningName`、`lastFinishedAt`、`cooldownTimer`、`stopped` 作为实例字段。
- `schedule()`、`processQueue()`、`stop()` 作为类方法。
- 模块创建一个默认单例，保持现有 handler 通过 `schedule()` 和 `stop()` 调用的方式不变。
- 测试通过 `new XuiJobScheduler({ cooldownMs })` 创建隔离实例。
- 本次调整只改变代码组织方式，不改变 FIFO、同名合并、结束后冷却、异常隔离和停止清理语义。

项目协作规则同步增加：包含多个方法和内部状态的模块优先使用 class 封装，避免使用工厂函数内嵌套定义多个函数并通过闭包保存状态。
