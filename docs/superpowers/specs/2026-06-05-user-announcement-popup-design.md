# 用户端首页公告弹窗设计方案

## 背景

当前系统已经具备公告管理能力：

- 管理端可新增、编辑、删除系统公告
- 用户端首页右侧已展示系统公告列表
- 公告内容已支持 Markdown 渲染

本次需要在用户端进入首页后增加“系统公告弹窗”能力，但弹窗并不是每次进入首页都展示，而是由管理端为公告配置“弹窗显示次数”，并按“每个用户单独计数”的方式决定后续登录是否继续展示。

同时，本次弹窗只展示“最近一条系统公告”，并复用现有公告内容的 Markdown 展示能力。

## 目标

- 用户端进入首页时，支持展示最近一条启用的系统公告弹窗
- 弹窗内容支持 Markdown 渲染
- 管理端在公告编辑时可配置弹窗显示次数
- 弹窗显示次数按“每个用户、每条公告”独立计数
- 只有用户点击关闭弹窗后，才计入一次已展示次数
- 当公告切换为新的公告 ID 后，新的计数自然重新开始
- 移动端弹窗必须自适应手机屏幕宽度，不允许溢出屏幕

## 非目标

- 本次不新增单独的公告详情页
- 本次不改动右侧“系统公告列表”的基础展示逻辑
- 本次不支持多条公告轮播或多条公告同时弹窗
- 本次不引入前端本地缓存计数作为主计数来源
- 本次不更新 `docs/api.md` 和 `docs/requirements.md`，除非实现完成后用户另行确认

## 业务规则

### 1. 公告选择规则

- 只考虑“启用状态”的系统公告
- 只取最近创建的一条启用公告作为弹窗候选
- 即使更早的公告设置了弹窗次数，也不参与本次首页弹窗判断

### 2. 显示次数规则

- 弹窗显示次数按“每个用户”单独计数
- 弹窗显示次数按“每条公告”独立计数
- `popup_show_limit = 0` 表示永不弹出
- `popup_show_limit > 0` 表示当前公告对每个用户最多弹出对应次数
- 当用户对当前公告的 `shown_count >= popup_show_limit` 时，后续登录不再弹出

### 3. 计数时机规则

- 首页加载时，后端只判断是否应该弹出，不立即加次数
- 前端真正显示弹窗后，仍不立即加次数
- 只有用户主动关闭弹窗后，前端才调用关闭上报接口
- 后端收到关闭上报后，才将该用户对该公告的 `shown_count + 1`

### 4. 公告切换规则

- 计数与 `announcement_id` 绑定
- 管理端新建一条更晚的启用公告后，用户首页只判断这条新公告
- 新公告会自动使用新的计数记录，不复用旧公告的展示次数

## 方案选择

本次采用“后端持久化用户-公告弹窗计数”的方案，而不采用前端 `localStorage` 计数。

原因：

- 能保证跨设备、跨浏览器、清缓存后仍然保持一致
- 更符合“用户后续登录还需不需要显示”的业务语义
- 是否展示由服务端统一判断，前端无需自行推导业务条件

## 数据模型设计

### 1. 公告表扩展

现有 `announcements` 表新增字段：

- `popup_show_limit`
  - 类型：整数
  - 默认值：`0`
  - 含义：弹窗显示次数上限，`0` 表示永不弹出

说明：

- 该字段属于公告配置的一部分，应由管理端创建和编辑公告时维护
- 该字段不影响现有右侧公告列表展示，只影响首页弹窗逻辑

### 2. 新增用户公告弹窗计数表

建议新增表：`user_announcement_popup_stats`

字段建议：

- `id`
- `user_id`
- `announcement_id`
- `shown_count`
- `created_at`
- `updated_at`

约束建议：

- `user_id + announcement_id` 唯一约束

字段语义：

- `shown_count`：该用户对该条公告已完成“关闭弹窗”的次数

## 后端设计

## 1. Repository 层

建议在公告仓储中补充以下能力：

- 查询最近一条启用公告
- 查询某个用户对某条公告的弹窗计数
- 创建或更新某个用户对某条公告的弹窗计数

建议新增仓储文件或在现有仓储中补充：

- `server/repositories/announcement-repository.js`
- `server/repositories/user-announcement-popup-repository.js`

职责划分：

- `announcement-repository.js`
  - 负责公告本身的读取与更新
- `user-announcement-popup-repository.js`
  - 负责用户公告弹窗计数记录的查询与累加

## 2. 管理端 Service / Controller

需要扩展现有公告新增与编辑逻辑：

- 创建公告时支持写入 `popup_show_limit`
- 编辑公告时支持更新 `popup_show_limit`
- 列表返回中包含 `popup_show_limit`，供管理端回显

校验规则：

- `popup_show_limit` 必须是大于等于 `0` 的整数
- 未传时使用默认值 `0`

## 3. 用户端 Service / Controller

建议新增一个专门用于首页弹窗判断的接口，而不是与公告列表接口混用。

推荐原因：

- 语义更清晰
- 避免首页右侧公告列表与弹窗业务耦合
- 后续若弹窗判断规则扩展，不会污染普通列表接口

建议新增用户侧能力：

- 获取最近公告弹窗信息
- 上报用户已关闭弹窗

## 接口设计

### 1. 管理端公告新增 / 编辑

沿用现有接口：

- `POST /api/admin/announcements`
- `PUT /api/admin/announcements/:id`

请求体新增字段：

- `popup_show_limit`

返回数据中新增字段：

- `popup_show_limit`

### 2. 用户端获取首页弹窗公告

建议新增接口：

- `GET /api/user/announcements/popup/latest`

返回语义：

- 当前是否存在可弹出的最新公告
- 当前公告的基础内容
- 当前用户对这条公告的已关闭次数
- 当前是否应该展示弹窗

建议返回结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "announcement": {
      "id": 12,
      "title": "端午节通知",
      "content": "## 节日安排\n\n请留意公告",
      "created_at": 1749081600,
      "popup_show_limit": 3
    },
    "shown_count": 1,
    "should_popup": true
  }
}
```

特殊情况：

- 没有启用公告时，`announcement` 返回 `null`，`should_popup = false`
- 最新启用公告 `popup_show_limit = 0` 时，`should_popup = false`
- 当前用户已达次数上限时，`should_popup = false`

### 3. 用户关闭弹窗上报

建议新增接口：

- `POST /api/user/announcements/:id/popup-close`

请求语义：

- 当前用户关闭了首页弹窗
- 服务端据此将该用户对该公告的 `shown_count + 1`

服务端处理规则：

- 校验公告存在
- 校验公告仍为启用状态
- 若不存在对应计数记录，则创建后写入 `shown_count = 1`
- 若已存在，则执行 `shown_count + 1`

说明：

- 该接口不要求再次判断 `should_popup`
- 即使前端重复触发，也应保证接口逻辑稳定，避免异常崩溃
- 是否需要额外防重由实现阶段评估，默认前端通过关闭按钮单次触发控制

## 用户端交互设计

### 1. 触发时机

首页视图加载完成后：

1. 获取用户资料与现有首页数据
2. 调用最新弹窗公告接口
3. 若 `should_popup = true`，显示公告弹窗
4. 用户关闭弹窗时，再调用关闭上报接口

### 2. 展示内容

弹窗仅展示最近一条系统公告：

- 标题
- 发布时间
- Markdown 内容

不额外展示：

- 多条公告切换
- 上一条 / 下一条
- 公告历史列表

### 3. Markdown 渲染

用户端弹窗应复用当前首页公告区域已使用的 Markdown 渲染能力：

- 使用现有 `marked` 渲染链路
- 保持与首页右侧系统公告内容的样式一致或高度接近

### 4. 关闭行为

用户点击关闭按钮后：

1. 先关闭前端弹窗
2. 再异步调用关闭上报接口

处理原则：

- 不能因为上报失败导致用户无法关闭弹窗
- 上报失败时仅记录错误日志或给出轻量提示，不阻塞主流程

## 管理端交互设计

管理端公告管理页在新增与编辑弹窗中新增字段：

- 字段名：弹窗显示次数
- 输入类型：整数输入框
- 提示文案：`0 表示永不弹出，正整数表示每个用户最多弹出次数`

交互规则：

- 新建公告默认值为 `0`
- 编辑公告时回显已有值
- 仅允许输入大于等于 `0` 的整数

列表页建议增加一列：

- `弹窗次数`

用于快速区分：

- `0`：不弹窗
- `> 0`：有限次弹窗

## 移动端适配设计

首页公告弹窗必须针对移动端做明确约束，避免在手机屏幕上溢出。

要求如下：

- 在手机宽度下，弹窗宽度应使用相对宽度，例如 `90vw` 到 `94vw`
- 弹窗最大宽度需要受限，避免桌面端过宽
- 弹窗内容区需要可纵向滚动，避免长公告把底部按钮挤出屏幕
- 弹窗整体最大高度应受限于视口高度，例如不超过 `80vh` 或相近范围
- 弹窗正文内的 Markdown 元素需要允许换行与横向滚动：
  - 长链接自动换行
  - 代码块允许横向滚动
  - 表格在小屏上不撑破容器

建议样式策略：

- 桌面端：固定宽度，例如 `720px` 左右
- 平板端：使用较宽比例布局
- 手机端：使用接近全宽的弹窗，并保留左右安全边距

建议重点验证宽度：

- `375px`
- `390px`
- `430px`

## 数据流

1. 用户进入首页
2. 前端请求 `GET /api/user/announcements/popup/latest`
3. 后端查询最近一条启用公告
4. 后端读取该用户对该公告的 `shown_count`
5. 后端根据 `popup_show_limit` 与 `shown_count` 计算 `should_popup`
6. 前端若收到 `should_popup = true`，展示弹窗
7. 用户点击关闭
8. 前端请求 `POST /api/user/announcements/:id/popup-close`
9. 后端将该用户对该公告的 `shown_count + 1`

## 测试设计

### 后端测试

需要覆盖：

- `popup_show_limit` 新增字段的创建与编辑
- `popup_show_limit = 0` 时不弹出
- 查询最近启用公告的逻辑正确
- 同一用户、同一公告的 `shown_count` 正确累计
- 不同用户之间计数互不影响
- 不同公告之间计数互不影响
- 达到上限后 `should_popup = false`
- 关闭上报接口首次写入与后续递增均正确

### 前端测试

需要覆盖：

- 管理端公告编辑弹窗可正确录入和回显 `popup_show_limit`
- 用户端首页可按 `should_popup` 正确展示或不展示弹窗
- 公告弹窗支持 Markdown 渲染
- 用户关闭弹窗后会发送一次关闭上报请求
- 上报失败不影响弹窗关闭

### 响应式验证

需要验证：

- 手机宽度下弹窗不溢出屏幕
- 长 Markdown 内容时弹窗内容区可滚动
- 代码块、长链接、表格不会撑破弹窗
- 桌面端样式不影响现有首页布局

## 风险与规避

### 风险 1：同一用户快速重复关闭导致重复计数

规避：

- 前端关闭按钮触发后立即销毁弹窗或设置一次性状态
- 后端逻辑保持幂等友好，至少保证异常不会影响主流程

### 风险 2：最新公告关闭上报失败，导致下次仍继续弹出

规避：

- 这是可接受的降级行为，因为业务以服务端持久化计数为准
- 实现时记录错误日志，便于排查

### 风险 3：移动端公告内容过长导致操作区不可见

规避：

- 弹窗内容区与整体高度做双重限制
- 关闭按钮保持在可触达区域内

## 实施边界

本次开发建议保持最小改动：

- 复用现有公告内容与 Markdown 渲染
- 复用现有首页公告展示数据来源
- 仅新增弹窗所需的独立查询与关闭上报接口
- 不对现有右侧公告列表做大规模结构改造
